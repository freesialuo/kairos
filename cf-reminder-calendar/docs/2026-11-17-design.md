# Personal Reminder Hub — Design

Date: 2026-11-17 · Status: approved by the user on 2026-11-17

## 1. Intent

A single-user "reminder hub" that runs on Cloudflare and needs no always-on machine of its own.

- Two event sources: (1) external ICS subscription URLs pulled on a schedule (class timetable, work calendar, public holidays, etc.); (2) events written by scripts / services through an authenticated API.
- When an event is near, the backend wakes up on its own **with nobody visiting the site** and sends a reminder through Bark (other channels such as a bot can be added later).
- A logged-in web page: view the merged calendar, manage subscription sources, configure notifications, etc.
- Low resource usage; nothing should spin while idle.

## 2. Goals / Non-goals / Anti-goals

**Goals**
- Merge both sources and remind at the correct time (including recurring events and time zones).
- Background scheduling does not depend on page visits and does not run while idle.
- Passkey login, multiple keys, with a recovery code as fallback.
- Runs within the Workers Free plan by default.

**Non-goals (not in v1)**
- Multiple users, shared calendars.
- Publishing an outbound ICS feed (this system is not a feed for calendar apps).
- Writing back to external ICS sources (pull-only).
- Telegram bot notifications (the channel interface leaves room; add later).
- Interaction inside a bot chat (snooze, creating events in natural language).
- Native apps.

**Anti-goals (a failure even if it technically runs)**
- **Silent failure** of reminders: failed sends or failed syncs invisible to the user.
- Duplicate spam: the same reminder pushed repeatedly.
- Wrong times: time zones, DST, or recurrence rules miscalculated so reminders fire at the wrong moment.
- Unexpectedly exceeding the free quota or incurring a bill.

## 3. Constraints (verified against official docs, 2026-11)

- Workers Free: **10 ms CPU** per invocation (time waiting on network / storage does not count); 100,000 requests per day; at most 50 subrequests per invocation. Static asset requests are free and unlimited.
- SQLite-backed Durable Objects are available on Free: 5 million rows read / day, 100,000 rows written / day, 5 GB total storage; each `setAlarm()` counts as one row written.
- DO alarms: one alarm per object at a time; `alarm()` has **at-least-once** execution (it may run more than once); an uncaught exception is retried with exponential backoff starting at 2 s, up to 6 retries; an alarm invocation has a 15-minute wall-time limit. Official guidance: catch exceptions inside the handler and re-arm the alarm yourself.
- KV: eventually consistent (changes may take 60 s+ to be visible in other locations), 1,000 writes / day on Free — this project **does not use KV**.
- Passkeys are bound to the domain (RP ID); changing the domain after deployment invalidates every key.
- ⚠️ For the builder to verify: whether a DO's per-invocation CPU limit on Free is also 10 ms. The design already copes by doing only small chunks of work per alarm; if parsing a large ICS still exceeds it, upgrading to the $5/month Paid plan fixes it without architectural change.

## 4. Approaches (chosen: Approach 2)

| | Approach 1: D1 + Cron | **Approach 2: one Durable Object (SQLite) + alarm** ✅ | KV only (rejected) |
|---|---|---|---|
| Idle cost | wakes every minute (~1,440 / day) | sleeps until there is work | — |
| Reminder precision | minute | second | — |
| Concurrency / duplicate sends | two cron runs can overlap; needs extra locking | single-threaded, no concurrency; only the alarm's at-least-once replay to handle | eventually consistent; prone to duplicates / misses |
| Inspecting data | SQL directly in the dashboard | via web export | — |
| Why rejected | — | — | low write quota, no time-range queries, weak consistency |

Why Approach 2: single user = single instance, the textbook Durable Object use case; a precisely timed alarm is exactly the "low-cost background process of its own" the user asked for; data and scheduler live in one place with strong consistency. The cost (no direct data inspection) is offset by an "export backup" on the web page.

## 5. Decided design

### 5.1 Architecture

```
Browser / scripts
   │
   ▼
Worker (entry)
   ├─ static assets: the web front end (free, not counted as requests)
   └─ /api/*, /auth/*  ──►  Durable Object "Hub" (single instance, idFromName("main"))
                              ├─ embedded SQLite: all data
                              ├─ auth: sessions, passkeys, API tokens
                              ├─ alarm(): send reminders + sync sources + maintenance
                              └─ outbound: fetch ICS, call Bark
```

Authentication is checked inside the DO (that is where the data lives); the Worker only routes and serves static assets.

### 5.2 Data (SQLite inside the DO; table names are suggestions)

- `sources`: subscription sources (URL, name, color, enabled, sync interval, default lead time, whether to honor in-feed VALARM, ETag / Last-Modified, last sync time / result, consecutive failure count).
- `events`: master event records. Origin `ics | api | manual`. Identity: ICS uses `(source_id, UID, RECURRENCE-ID)`; API uses a caller-supplied `external_id` (idempotent upsert). Fields include title, start / end, all-day, time zone, location, description, RRULE / EXDATE, custom reminder lead times.
- `occurrences`: instances of (recurring) events expanded within a **rolling 60-day window** (recomputed on every sync and in daily maintenance).
- `reminders`: one row per occurrence × lead time, with `fire_at`, status (pending / sent / failed / skipped), attempt count, next retry time.
- `deliveries`: send log (time, channel, result, error message), shown on the Log page.
- `channels`: notification channel configuration.
- `passkeys`: credential ID, public key, device name, created / last-used time.
- `sessions`, `api_tokens` (hashes only), `settings` (time zone, default lead time, all-day reminder time, etc.).

### 5.3 Background scheduling (the core)

A single alarm, always set to the **minimum** of: the next pending reminder, the next pending retry, the next due source sync, the next daily maintenance.

Each `alarm()`:
1. Send every pending reminder with `fire_at <= now` (one by one, recording status immediately).
2. If any source is due, sync **only one** of them (bounds per-invocation CPU).
3. When due, run daily maintenance: roll the expansion window forward, purge old data (delivery log kept 90 days).
4. Compute the next time and `setAlarm()`.

The whole handler is wrapped in try/catch and **re-arms the alarm whether it succeeds or fails**, rather than relying on the platform's 6 retries. Every write from the web page or API also recomputes the alarm (a new reminder may be earlier than the current alarm).

**Duplicates**: the DO is single-threaded, so there are no concurrent duplicates; the only duplicate path is "push succeeded, crash before the status write" followed by an alarm replay. That is very unlikely and acceptable (better an occasional duplicate than a missed reminder).

### 5.4 Source sync

- Each source syncs every 30 minutes by default (minimum 15 minutes, configurable per source).
- Conditional requests with ETag / Last-Modified; skip parsing when unchanged.
- 5 MB size cap per ICS; exceeding it counts as a failed sync and is surfaced.
- Add / update / delete by UID: an event removed upstream → its unsent reminders are removed; an event rescheduled upstream → unsent reminders are rescheduled to the new time.
- 3 consecutive failures → send one "source X failed to sync" notification through the channel, and flag it in red on the web page.

### 5.5 Reminder rules

- Lead-time precedence: the event's own (API-specified / in-feed VALARM, if that source has "honor VALARM" on) → the source default → the global default (15 minutes). An event may have several lead times.
- All-day events: remind at 09:00 on the day (user time zone; configurable in Settings).
- Time zones: one global user time zone setting; ICS times with a TZID use that zone; floating times are interpreted in the user time zone. DST is handled by the time-zone library.
- Late reminders (e.g. an event just added whose reminder time has passed): if the event has not started → send immediately, marked as late; if it has started → skip and record as skipped.
- Send failures: retry after 1, 5, and 15 minutes; still failing after 3 retries → mark failed and highlight it on the Log page.
- Message content: title, time (including "in X minutes"), location, source name, link to the web page.

### 5.6 Notification channels

- A uniform interface: `send(message) → success / failure (error message)`; adding Telegram bot or another channel later means adding one implementation.
- v1 implements **Bark only** (server URL + device key; self-hosted Bark servers supported).
- Settings offers "send a test notification".

### 5.7 Authentication

**Web: Passkey (WebAuthn)**
- **Domain**: a custom domain or `*.workers.dev` are both fine, fixed **once** at deployment through configuration (e.g. `RP_ID` / `ORIGIN`) and not changed in principle.
- **If the domain does change**: all old keys stop working → log in with the recovery code → register new keys, i.e. back to the first-time setup flow. To support this, each key records the RP ID it was registered under; login only uses keys matching the current RP ID, and non-matching ones are marked "invalid" in Settings for cleanup.
- Multiple keys can be registered (each named) and revoked in Settings; revoking the last key shows a warning.
- **Recovery code**: set at deployment via `wrangler secret`. Uses:
  1. **First-time setup**: while no key exists, the recovery code must be entered before the first key can be registered (prevents someone else claiming a fresh deployment).
  2. **Lost keys**: after logging in with the recovery code, the user is forced into "register a new key".
  - Wrong recovery-code attempts are rate-limited: 5 per hour, then locked for 1 hour.
  - The recovery code does not expire after use; to change it, set the secret again.
- The login challenge lives in a **signed, short-lived cookie** (valid 2 minutes, HMAC-signed), never in storage.
- Sessions: a random ID in an HttpOnly + Secure + SameSite=Strict cookie, stored server-side in SQLite; 30-day sliding expiry; supports logout and "log out all devices". State-changing requests also check the Origin header.

**API: Bearer token**
- Created on the Settings page, **shown only once**; the server stores only its SHA-256 hash, plus name and last-used time; revocable.
- Scope: may only read and write events of origin `api`; cannot change settings, sources, or keys.

### 5.8 Web pages

| Page | Contents |
|---|---|
| Calendar | Month / week view, all sources merged, one color per source; clicking an event shows details and its reminder status |
| Sources | Add / remove, enable / disable, sync interval, default lead time, honor VALARM, last sync result, "sync now" |
| Events | Create / edit / delete events manually (origin `manual`); ICS events are read-only; API events can only be deleted on the web, not edited (the next API write would overwrite the edit) |
| Settings | Time zone, default lead time, all-day reminder time; notification channel and test; passkey management; API token management; export backup (full JSON + ICS) |
| Log | Reminder send history with failures pinned to the top and highlighted; source sync errors |

### 5.9 API (v1 draft)

- `PUT /api/v1/events/{external_id}` — idempotent upsert. Fields: `title`, `start`, `end`, `all_day`, `timezone`, `location`, `description`, `rrule` (optional), `reminders` (array of lead minutes, optional).
- `GET /api/v1/events?from=&to=` — list by time range (ICS events included, read-only).
- `DELETE /api/v1/events/{external_id}`
- Times are ISO 8601; times without an offset are interpreted in the `timezone` field or else the user time zone.

## 6. Left to the builder

- Front-end framework and UI styling.
- ICS parsing and recurrence-expansion library: must support RRULE / EXDATE / RECURRENCE-ID / TZID and run in the Workers runtime.
- WebAuthn server library (must be compatible with the Workers runtime).
- Table schema details, indexes, migration approach.
- Verify the CPU limit flagged ⚠️ in section 3, and measure one sync's CPU time against a real large ICS.

## 7. Decisions made by Claude in this document (can be overturned)

- Events can be created manually on the web page.
- 60-day expansion window; delivery log kept 90 days.
- Global default lead time 15 minutes; all-day events reminded at 09:00 on the day.
- Sources sync every 30 minutes by default (minimum 15), 5 MB cap per source, push an alert after 3 consecutive failures.
- Late-reminder send / skip rule; 3 retries on failure.
- API tokens may only operate on `api`-origin events.
- The recovery code also gates first-time setup.
- Better a very unlikely duplicate than a missed reminder.
- API events can only be deleted on the web, not edited; the recovery code does not expire after use.
