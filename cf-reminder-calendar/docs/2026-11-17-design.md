# Personal Reminder Hub — Architecture Design

> **Superseded on 2026-11-18** by `2026-11-18-rust-architecture.md` (all-Rust implementation). Kept for history.

Date: 2026-11-17 · Status: product scope approved by the user on 2026-11-17; architecture revised the same day after plan review (see §21 Revision log).

## 1. Intent

A single-user, serverless personal reminder hub on Cloudflare Workers that runs on its own, with no always-on host and no need for anyone to have the site open.

- **Two event sources, plus manual entry:** (1) external ICS subscription feeds pulled on a per-source schedule (class timetables, work calendars, public holidays); (2) events pushed by scripts or services through an authenticated REST API; plus events created by hand in the web UI.
- **Reminders sent on its own:** the backend wakes itself before an event starts, **even when nobody is visiting the site**, and sends a reminder through Bark. Bark sits behind a channel interface, so a Telegram bot or another channel can be added later.
- **Management UI behind login:** a passkey-protected web app to view the merged calendar, manage feeds, configure notifications and time zone, and read the delivery log.
- **Nothing runs while idle:** no compute, cron ticks, or storage writes between scheduled work items.

## 2. Goals / Non-goals / Anti-goals

**Goals**
- Merge ICS, API, and manual events into one timeline, and remind at the right time across recurring series, DST transitions, and mixed time zones.
- Run background scheduling independently of client visits. Sleep when idle; wake only when work is due.
- Protect the web UI with multiple WebAuthn passkeys, with a rate-limited recovery code for first-time setup and lost devices.
- Stay within the Cloudflare Workers Free plan under normal single-user load.

**Non-goals (v1)**
- Multiple users, accounts, or shared calendars.
- Publishing an outbound ICS / CalDAV feed.
- Writing back to external feeds (pull-only).
- Telegram bot delivery (the channel interface leaves room for it).
- Conversational bot features (snooze from a chat, natural-language event creation).
- Native mobile or desktop apps.
- `RDATE` support (detected and reported as a warning; see §9).

**Anti-goals (failures even if the system nominally runs)**
- **Silent failure:** dropped notifications, stalled syncs, truncated recurrence expansion, or broken feeds (such as HTML error pages served with HTTP 200) that the user never finds out about.
- **Duplicate spam:** the same reminder pushed repeatedly.
- **Wrong times:** reminders early, late, or on the wrong day because of time zones, DST shifts, or mishandled `RRULE` / `EXDATE` / `RECURRENCE-ID` / cancelled instances.
- **Quota surprises:** hot loops, chatty polling, or unbounded CPU or writes that exhaust Free plan limits or cause charges.

## 3. Platform Constraints (verified against official docs, 2026-11)

- **Workers Free:** 10 ms CPU per invocation (time spent awaiting network or storage I/O does not count); 100,000 requests/day; ≤ 50 subrequests per invocation. Static asset requests are free and unlimited.
- **SQLite-backed Durable Objects on Free:** 5 M rows read/day, 100 k rows written/day, 5 GB total. **Each `setAlarm()` is billed as one row written.**
- **Alarms:** at most one alarm per object. `alarm()` runs **at least once** (replays are possible). An uncaught exception is retried with exponential backoff starting at 2 s, at most 6 retries. 15-minute wall-clock limit per invocation. Official guidance is to catch errors inside the handler and re-arm explicitly.
- **KV is excluded:** it is eventually consistent (60 s+ to propagate), allows only 1,000 writes/day on Free, and has no range queries.
- **WebAuthn:** credentials are bound to the RP ID. Changing the hostname makes every existing key unusable.
- **⚠️ To verify on deploy:** whether the Durable Object CPU limit on Free is also 10 ms per `alarm()` / request. The architecture keeps **every** unit of work small (§7.1), so the only step that cannot be split is parsing one large feed. If that alone exceeds the limit, the Paid plan ($5/month) fixes it with no code change.

## 4. Approaches (chosen: Approach 2)

| Dimension | Approach 1: D1 + Cron Triggers | **Approach 2: one Durable Object (SQLite) + alarm** ✅ | KV only (rejected) |
|---|---|---|---|
| Idle overhead | Wakes every minute (~1,440/day) | Sleeps until the next scheduled moment | — |
| Precision | 1 minute | 1 second | — |
| Concurrency / duplicates | Cron runs can overlap; needs locking | Single-threaded; only alarm replay to guard against | Eventual consistency; misses and duplicates likely |
| Data inspection | SQL in the dashboard | JSON / ICS export in the UI | — |
| Why rejected | — | — | 1 k/day write cap, no range queries, weak consistency |

**Why Approach 2:** one user maps to one named Durable Object (`idFromName("main")`). Keeping the SQLite data, the auth state, and one self-arming alarm inside a single single-threaded object gives strong consistency, second-level precision, and zero idle wake-ups. Losing the dashboard SQL console is covered by JSON and ICS exports.

## 5. System Architecture

### 5.1 Context and components

```
             ┌──────────────┐        ┌──────────────────┐
  Browser ──►│              │        │ ICS feed servers │◄── HTTPS GET (conditional)
  (SPA)      │   Worker     │        └──────────────────┘
             │ entry router │                 ▲
  Scripts ──►│              │                 │
  (Bearer)   └──┬────────┬──┘        ┌────────┴─────────┐
                │        │           │  Hub (Durable    │──► Bark server (HTTPS POST /push)
     static     │        └─/api/*───►│  Object, single  │
     assets ◄───┘          /auth/*   │  instance "main")│
     (ASSETS binding,                │  ├ HTTP (Hono)   │
      SPA fallback)                  │  ├ auth          │
                                     │  ├ domain        │
                                     │  ├ scheduler ⏰   │
                                     │  └ SQLite        │
                                     └──────────────────┘
```

- **Worker (stateless):** with `run_worker_first: ["/api/*", "/auth/*"]`, only API and auth paths reach Worker code. They are forwarded unchanged to the Hub. Everything else is served from static assets with single-page-app fallback, without running Worker code.
- **Hub (stateful):** owns all data, enforces all authentication, and runs all background work. It has two entry points: `fetch()` (HTTP) and `alarm()` (scheduler).

### 5.2 Module layers inside the Hub

| Layer | Modules | Depends on | Notes |
|---|---|---|---|
| Entry | `hub.ts` (`fetch`, `alarm`, `rearm`, `deps`) | everything below | The only place that touches `ctx.storage` alarms |
| HTTP | `http/app.ts`, `auth-routes.ts`, `admin.ts`, `api-v1.ts`, `validate.ts` | auth, domain, scheduling | Hono router; every mutating route ends with `rearm()` |
| Auth | `auth/crypto`, `cookies`, `session`, `recovery`, `passkey`, `tokens` | storage, WebAuthn library | |
| Scheduling | `sched/scheduler`, `sched/dispatch`, `sched/queue`, `sources/sync` | domain, integration, storage | Every step bounded by a budget (§7.1) |
| Domain (pure) | `time/zone`, `ics/parse`, `ics/expand`, `calendar/reminders` (planning), `notify/message` | `ical.js`, `Intl` | No I/O and no clock; fully unit-testable |
| Domain (stateful) | `calendar/events`, `calendar/reminders` (reconcile) | storage, pure domain | Synchronous SQL |
| Integration | `notify/bark` (`Channel`), injected `fetch` | — | Behind `HubDeps` |
| Storage | `db/schema`, `db/settings` | DO SQLite API | Forward-only migrations |

**Dependency injection:** `Hub.deps = { now, fetch, channel, webauthn }`. Production uses the real clock, `fetch`, Bark, and `@simplewebauthn/server`. Tests replace any of them.

### 5.3 Runtime model

- One instance. All requests and alarms are serialized by the Durable Object's input gate, so the code never races itself.
- Schema migration runs once per cold start inside `blockConcurrencyWhile`.
- Writes that must change together (an event and its reminders, a queue item and its result) run inside `ctx.storage.transactionSync`.
- `rearm()` is the only function that calls `setAlarm()`. It skips the call when the target equals the current alarm, since every `setAlarm()` costs a row write.

## 6. Data Architecture

### 6.1 Conventions

- **Instants:** UTC epoch milliseconds (`INTEGER`).
- **Wall-clock times:** `YYYY-MM-DDTHH:mm:ss` (timed) or `YYYY-MM-DD` (all-day), paired with `tzid`, which is an IANA zone, `'UTC'`, or `NULL` for floating time (interpreted in the user's time zone).
- **Identity keys:**
  - `series_key`: `ics:<sourceId>:<uid>` · `api:<externalId>` · `manual:<eventId>`
  - `occ_key`: `<series_key>|<slot>`. `slot` is the occurrence's *original* wall-clock start for recurring series (the override's `RECURRENCE-ID`, which is the same value), or `single` for non-recurring events. An instance moved upstream therefore keeps its key.
  - reminder `key`: `<occ_key>|<leadMin>` (timed) or `<occ_key>|allday`.

### 6.2 Schema (migration 1)

```sql
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);          -- JSON values; 'meta:*' keys are internal
CREATE TABLE sources (
  id INTEGER PRIMARY KEY, name TEXT NOT NULL, url TEXT NOT NULL, color TEXT NOT NULL,

  honor_valarm INTEGER NOT NULL DEFAULT 1, etag TEXT, last_modified TEXT, last_sync_at INTEGER,
  last_result TEXT, last_error TEXT, consecutive_failures INTEGER NOT NULL DEFAULT 0);

  id INTEGER PRIMARY KEY, origin TEXT NOT NULL, source_id INTEGER, series_key TEXT NOT NULL,

  hash TEXT NOT NULL, updated_at INTEGER NOT NULL,

  id TEXT PRIMARY KEY, public_key BLOB NOT NULL, counter INTEGER NOT NULL, transports TEXT,

  id_hash TEXT PRIMARY KEY, scope TEXT NOT NULL, created_at INTEGER NOT NULL,
```

**Settings keys:** `timezone` (default `'UTC'`; set to the browser zone during first-time setup), `defaultLeadMin` (15), `allDayTime` (`'09:00'`).
**Meta keys:** `meta:last_maintenance_at`, `meta:last_maintenance_error`, `meta:alarm_error_streak`, `meta:last_alarm_error`, `meta:recovery_locked_until`, `meta:webauthn_user_id`.

### 6.3 Data roles and invariants

- **`events`** is the source of truth for what is scheduled.
- **`reminders`** is the *current schedule*, not a history. When an event moves, its reminder row is rewritten in place, even if it was already sent. **History lives in `deliveries`**, an append-only log of every send attempt, skip, and alert, kept for 90 days.
- **No `occurrences` table.** Occurrences are expanded when needed. Each reminder row carries `occ_start_utc`, so dispatch never expands anything.
- **`reconcile_queue`** lists series whose reminders must be recomputed. Bulk changes go through it so no single invocation does unbounded work.
- **Invariant 1:** every `pending` reminder belongs to an existing `events` row. Dispatch double-checks and deletes orphans without sending.
- **Invariant 2:** every background step leaves a durable trace of progress (an updated timestamp, cursor, attempt count, or error record) before the invocation ends, **success or failure**. This is what rules out hot loops (§7.2).

## 7. Core Flows

### 7.1 Alarm cycle

Each `alarm()` runs these steps in order. Each step has a budget, and each step's failure is caught **separately**, so one broken step cannot starve the others:

| # | Step | Budget per wake | On unexpected exception |
|---|---|---|---|
| 1 | **Dispatch** due reminders (`pending`, `next_attempt_at <= now`, oldest first) | ≤ 20 reminders | Counted as a failed send attempt for that reminder (retry schedule applies); continue with the next one |
| 2 | **Reconcile queue**: recompute queued series (`not_before <= now`, oldest first) | ≤ 10 series | Queue item `attempts += 1`, `not_before = now + 2^attempts min`; after 3 attempts the item is dropped and the error is written to the series' `expand_warning` and the Log |
| 3 | **Sync** one due source | 1 source | Treated as a sync failure (§7.5); `last_sync_at = now` is always written |
| 4 | **Maintenance**, if due | 1 pass | `meta:last_maintenance_error` set; `last_maintenance_at = now - 23 h`, so the next try is in 1 hour |
| 5 | **Re-arm**, in `finally` | — | — |

A top-level `try/catch` around the whole sequence is the last line of defense (§7.2).

**Maintenance pass (daily):** queue every *recurring* parent series with reason `roll` (the 60-day window moves forward; non-recurring events need nothing); delete `deliveries` and non-`pending` reminders older than 90 days; delete expired `sessions`; delete `auth_failures` older than 1 hour; set `meta:last_maintenance_at = now`.

### 7.2 Next-alarm computation and backoff

`computeNextAlarm(now)` takes the minimum of:
1. `MIN(next_attempt_at)` over `pending` reminders;
2. `MIN(not_before)` over `reconcile_queue`;
3. for each enabled source, `last_sync_at + interval_min` (or `now` if never synced);
4. `meta:last_maintenance_at + 24 h` (or `now` if never run).

`rearm()` sets `target = max(computeNextAlarm(now), floor)`:
- **Normal floor:** `now + 1 s`. This drains backlogs quickly (more than 20 due reminders, a long reconcile queue) without busy-waiting inside a single invocation.
- **Error floor:** if the top-level catch fired in this alarm, `meta:alarm_error_streak += 1` and the floor becomes `now + min(2^(streak − 1), 15)` minutes (1, 2, 4, 8, 15). A clean run resets the streak to 0. The streak and last error are shown in the Log under "Background errors".

Together with Invariant 2, this bounds worst-case wake-ups. Even a step that throws on every run makes durable progress or backs off, so a permanent bug costs at most about 4 wake-ups per hour, not 86,400 per day.

### 7.3 Reconciliation: inline vs queued

`reconcileSeries(series)` expands the series over `[now, now + 60 days)`, plans reminders (§7.6), and diffs them against the series' existing reminder rows:

| Planned vs stored | Action |
|---|---|
| Planned, not stored | Insert `pending`, `next_attempt_at = fire_at` |
| Stored `pending`, `fire_at` changed | Update `fire_at`, `next_attempt_at`; reset `attempts`, `late`, `last_error` |
| Stored `sent` / `skipped` / `failed`, `fire_at` changed (event rescheduled) | Rewrite the row as `pending` with the new time (the earlier outcome stays in `deliveries`) |
| Stored `pending`, no longer planned | Delete (with a `deliveries` row `kind='reminder'`, `ok=0`, `error='withdrawn: event changed or removed'` only if `attempts > 0`, so retries in flight are not lost silently) |
| Stored finished row, no longer planned | Keep until the 90-day purge |

**When it runs:**
- **Inline**, inside the same request/transaction: single-series edits, meaning API upsert/delete and manual create/edit/delete. A reminder for a just-created event exists before the response returns.
- **Queued:** anything that can touch many series:
  - settings change: `timezone` / `allDayTime` → floating and all-day series; `defaultLeadMin` → all series;
  - source settings change: that source's series;
  - source sync: each changed, created, or pruned series;
  - daily window roll: recurring series.

  The response returns immediately. The UI shows "Recomputing reminders… N left" from the queue length. The queue drains at 10 series per wake, about one wake per second.

### 7.4 Recurrence expansion

`expandSeries(rows, fromUtc, toUtc, userTz)` takes a parent row plus its override rows and returns `{ occurrences, anchor, status, warning }`.

**Algorithm**
1. Zone per row is `tzid ?? userTz`.
2. The suppressed slot set is the parent's `exdates` (which, after parsing, include cancelled instances, §9) plus every override's `recurrence_id`.
3. **Non-recurring parent:** one occurrence, slot `single`.
4. **Recurring parent:**
   - Iterate the RRULE (`ical.js` `Recur.iterator`) over *floating wall-clock* slots, convert each with `wallToUtc(slot, zone)`, and drop suppressed slots and slots before `fromUtc`. Stop at `toUtc` or when the rule ends.
   - Iteration starts at the **anchor** when it is usable, otherwise at `DTSTART`.
5. **Each override row:** one occurrence with slot = its `recurrence_id`, emitted independently. An override whose parent is missing from the feed still produces its occurrence.

**Anchor (resume point).** Expanding from `DTSTART` every time is unbounded: a daily series started 15 years ago needs about 5,500 iterations before reaching today. So:
- The anchor is `{ slot, index, hash }`. `slot` is the last raw RRULE slot whose start is `< now − 1 day`. `index` is its 0-based position in the raw slot sequence, counting slots later removed by EXDATE, because they still count toward `COUNT`. `hash` is the parent row's content hash.
- **Resuming:** rebase the rule with `DTSTART := anchor.slot` and, if the rule has `COUNT`, `COUNT := COUNT − anchor.index`. `UNTIL`, `INTERVAL`, and `BY*` parts are unchanged. Because the anchor is a real occurrence, the rebased rule generates exactly the tail of the original sequence.
- The anchor is used only when `anchor.hash === row.hash`, the anchor's start is `≤ fromUtc`, and the rule has no `BYSETPOS`. `BYSETPOS` rules always iterate from `DTSTART`, within the budget.
- Reconciliation persists the new anchor. It only moves forward, at most once per series per daily roll.

**Budgets and status**
- **Budget:** at most 2,000 raw slots per call.
- **Catching up:** if the budget runs out before reaching `fromUtc` (a very old, very frequent series), return status `catching_up` and an anchor at the furthest slot reached. Reconciliation saves that progress and re-queues the series, so the next wake continues from there.
- **Too dense:** if the budget runs out inside the window (for example a rule repeating every minute), return status `too_dense` with the occurrences found so far, and the warning `Recurrence too dense; only the first N occurrences in the window are scheduled`.
- **Surfacing:** a non-`complete` status is stored on the parent row and shown on the event, on its source, and in the Log.

**Calendar view queries** use the same function with the requested range (≤ 92 days). For ranges before the anchor, expansion starts at `DTSTART` within the budget. If it is truncated, the response marks the series `truncated: true` and the UI shows a hint.

### 7.5 Source sync

1. **Pick:** the oldest due enabled source.
2. **Fetch:** a conditional `GET` with `If-None-Match` / `If-Modified-Since`. `304` → `last_result = 'unchanged'`, failures reset, no parsing.
3. **Guard:**
   - Size: reject if `Content-Length > 5 MB`. Otherwise stream the body while counting bytes, and abort at 5 MB.
   - Format: `parseIcs` must find a root `VCALENDAR`, so an HTML page served with 200 fails here.
   - Errors: any non-2xx status, network error, guard failure, **or any unexpected exception** is a failure.
4. **On success:**
   - Upsert every parsed row as origin `ics`. Prune rows of this source that are no longer in the feed: deleted series, and stale overrides of series that still exist.
   - Enqueue each changed, created, or pruned series (reason `sync`).
   - Store the new validators, reset `consecutive_failures`, and set `last_result = 'ok: N events'` followed by any parse warnings.
5. **On failure:**
   - Existing events and reminders are left untouched.
   - `consecutive_failures += 1`, `last_error` is set, `last_sync_at = now`.
   - When `consecutive_failures` becomes exactly 3, send one source alert through the channel and log it (`kind='source_alert'`).
6. **Always:** `last_sync_at` is written, whatever happened (Invariant 2).

### 7.6 Reminder planning and dispatch

**Planning (pure):**
- **Timed occurrences:** one reminder per lead time. Lead times resolve in this order:
  1. the event's explicit `lead_minutes`;
  2. the feed's `VALARM` minutes, if the source honors VALARM and any exist;
  3. the source's `default_lead_min`;
  4. the global `defaultLeadMin`.

  Duplicates are removed. `fire_at = occ_start − lead`.
- **All-day occurrences:** exactly one reminder at `allDayTime` on the event date in the effective zone. Lead times do not apply.

**Reminder lifecycle:**

```
            planned
               │
               ▼
   ┌──────► pending ──send ok──────────────► sent
   │           │ │
   │           │ └─send failed (attempt n)──► pending (next_attempt_at = now + 1/5/15 min)
   │           │        └─after 4th failed attempt (1 initial + 3 retries)──► failed
   │           ├─event already started, attempts = 0──► skipped
   │           ├─event already started, attempts > 0──► failed
   │           ├─no channel configured──► failed
   │           └─event row missing──► (deleted, never sent)
   └──── rescheduled (any state, fire_at changed) ◄── reconcile
```

- **Late send:** if `now − fire_at > 2 min` while the event has not started, the message is sent with a `(late)` prefix and `late = 1`.
- **Order of writes:** the status is persisted immediately after each send, and every attempt appends a `deliveries` row.
- **Accepted risk:** the only path to a duplicate is "push succeeded, then crash before the status write, then alarm replay". This is accepted as better than missing a reminder.

## 8. Time Model

- **Conversion:** `wallToUtc(wall, zone)` uses `Intl.DateTimeFormat`, which has full ICU zone data in Workers.
  - Let `g` be the wall time read as if it were UTC. Sample the zone's offsets at `g − 24 h` (`pre`) and `g + 24 h` (`post`), and form the candidates `g − pre` and `g − post`.
  - **Normal and fall-back overlap:** take the earliest candidate whose wall time round-trips to `wall`. In an overlap both round-trip, so this picks the earlier instant.
  - **Spring-forward gap:** if no candidate round-trips, return `g − pre`. This always moves the wall time **forward** by the gap, in every hemisphere and on either side of UTC. Examples: New York 2026-03-08 02:30 → 03:30 EDT; Berlin 2026-03-29 02:30 → 03:30 CEST.
  - Never use the offset sampled at `g` itself. For zones east of UTC it can already be the post-transition offset, which moves the time backward.
- **Recurring events** iterate in wall-clock time and convert each instance separately, so a weekly 09:00 event stays at 09:00 across DST.
- **Floating times** (`tzid NULL`) and **all-day events** follow the user time zone. Changing the time zone or the all-day time re-queues every affected series.
- **API times with an explicit offset** are stored as wall-clock time in `timezone ?? userTz`, with that zone made explicit. Their instant stays fixed if the user later changes the time zone.

## 9. ICS Support Matrix

| Feature | Handling |
|---|---|
| `DTSTART`/`DTEND`/`DURATION`, `TZID` (IANA), `Z` (UTC), floating | Supported |
| `TZID` not a valid IANA name (e.g. `China Standard Time`) | Treated as floating (user zone) + warning in `last_result` |
| `VALUE=DATE` all-day | Supported; default duration 1 day |
| `RRULE` (all FREQ/BY* parts supported by `ical.js`), `EXDATE` (multi-valued and repeated) | Supported; expansion as in §7.4 |
| `RECURRENCE-ID` override | Separate row, keeps the original slot's `occ_key` |
| `RECURRENCE-ID` + `STATUS:CANCELLED` (one instance cancelled) | **Merged into the parent's `exdates`**; the slot is suppressed, not resurrected |
| `STATUS:CANCELLED` on the master | Whole series dropped, including its overrides |
| Cancelled override whose master is absent | Ignored |
| Override whose master is absent | Kept as a stand-alone occurrence |
| `RANGE=THISANDFUTURE` | Treated as a single-instance override |
| `VALARM` with relative `TRIGGER ≤ 0`, `RELATED=START` (or default) | Converted to lead minutes |
| `VALARM` absolute or `RELATED=END` | Ignored |
| `RDATE` | Not supported in v1; warning `RDATE ignored on "<summary>"` |
| Not a `VCALENDAR` (HTML error page, empty body) | Sync failure; existing data untouched |

## 10. Notification Channels

- **Interface:** `Channel.send(message) → { ok: true } | { ok: false, error }`. Scheduling and retry logic know nothing about the transport.
- **Bark (v1):**
  - Request: `POST <server>/push`, JSON `{ device_key, title, body, url, group: 'reminders', level: 'timeSensitive' }`. The server is `https://api.day.app` by default, or a self-hosted server.
  - Success means HTTP 200 **and** response `code === 200`.
- **Message format:**
  - Title: `⏰ <title>`.
  - Body: `HH:mm · in N min` or `HH:mm · now` for timed events, `Today · all day` for all-day events; then the location and the source name.
  - Late sends get the `(late) ` prefix.
  - Link: `<ORIGIN>/calendar?event=<id>`.
- **Source alert:** title `⚠️ Source sync failing`, body `<name>: <error ≤ 200 chars>`, link `<ORIGIN>/sources`.
- **Diagnostics:** Settings has "Send test notification", which logs a `kind='test'` delivery.

## 11. Security Architecture

### 11.1 Principals and credentials

| Principal | Credential | Can access |
|---|---|---|
| Owner (web) | Passkey → `full` session | Everything under `/api/admin/*` and `/auth/*` |
| Owner recovering | Recovery code → `recovery` session | Only passkey registration (and logout) |
| Script | Bearer token `rh_…` | `GET /api/v1/events` (all origins, read-only); `PUT`/`DELETE` of `api`-origin events only |
| Anonymous | — | `GET /auth/state`, login and recovery endpoints, static assets |

### 11.2 Passkeys (WebAuthn)

- **Configuration:** `RP_ID` and `ORIGIN` are fixed once at deployment, either a custom domain or `*.workers.dev`.
- **Registration and login options:**
  - Discoverable credentials (`residentKey: 'required'`), so login needs no username.
  - `userVerification: 'preferred'` together with `requireUserVerification: false`, set consistently in **both** registration and authentication verification. A key without PIN or biometrics that can register can therefore also log in.
- **Stored per key:** id, public key (BLOB), counter, transports, `rp_id`, name.
- **Login** only considers keys whose `rp_id` equals the current `RP_ID`. Keys with another `rp_id` are shown as **stale** in Settings.
- **Key management:**
  - Rename: `PATCH /api/admin/passkeys/:id { name }`.
  - Revoke: `DELETE /api/admin/passkeys/:id`.
  - **Revoking the last valid key requires confirmation:** the first `DELETE` returns `409 { error: 'confirm_required', warning }`; the UI shows a confirmation dialog and repeats the request with `?confirm=1`.
- **Challenges** are stored in an HMAC-signed `__Host-chal` cookie, never in the database:
  - lifetime 2 minutes;
  - bound to its purpose, `reg` or `auth`;
  - cleared after use.

### 11.3 Recovery code

- Set with `wrangler secret put RECOVERY_CODE` and compared in constant time, by comparing SHA-256 digests.
- **Uses:**
  1. **First-time setup:** while no valid key exists for `RP_ID`, the first registration needs a recovery session. This stops strangers from claiming a fresh deployment.
  2. **Lost device or domain change:** the recovery session can only register a new passkey. Registering upgrades it to `full`.
- **Rate limit:** 5 wrong attempts within 1 hour → locked for 1 hour (`429`).
- **Lifetime:** the code stays valid until the secret is rotated.

### 11.4 Sessions and CSRF

- **Session cookie:** a random 32-byte token in `__Host-sid` (`HttpOnly; Secure; SameSite=Strict; Path=/`). Only its SHA-256 hash is stored.
- **Expiry:** 30-day sliding window. `expires_at` is refreshed at most once per day, to limit writes.
- **Logout:** of the current session, or "log out all devices".
- **CSRF:** every state-changing request under `/auth/*` and `/api/admin/*` must carry `Origin === ORIGIN`, otherwise `403`. Bearer-token routes are exempt because they use no cookies.

### 11.5 API tokens

- Format: `rh_` + 32 random bytes in base64url.
- Shown once when created. Only the SHA-256 hash is stored, plus a 10-character prefix for display, the name, and `last_used_at`.
- Revocable at any time.

### 11.6 Threats and mitigations

| Threat | Mitigation |
|---|---|
| Stranger claims a fresh deployment | First passkey requires the recovery code |
| Brute-forcing the recovery code | 5 attempts/hour + 1-hour lockout; long random code recommended (`openssl rand -base64 32`) |
| Stolen session cookie via XSS | `HttpOnly`; SPA renders all feed and event text as text, never as HTML; strict CSP on the SPA (`default-src 'self'`) |
| CSRF | `SameSite=Strict` + `Origin` check |
| Leaked API token | Hash-only storage, narrow scope, revocation, `last_used_at` visible |
| Malicious / huge feed | 5 MB cap, format guard, parse in a bounded step, text-only rendering |
| Feed URL pointing at internal services (SSRF) | Only `https://` URLs accepted; Workers cannot reach private networks |
| Secrets in exports | Export never includes passkeys, sessions, tokens, or the clear Bark key |

- Fields: `title` (1–200), `start` (ISO 8601 date or date-time), `end` (optional; default = start for timed events, start + 1 day for all-day), `all_day`, `timezone` (IANA), `location` and `description` (≤ 2,000 each), `rrule`, `reminders` (≤ 5 integers in 0–10,080).

## 14. Failure Modes and Resilience

| Failure | Detection | Behavior | Visible where |
|---|---|---|---|
| Bark down / bad key | Send result not ok | Retries +1/+5/+15 min, then `failed` | Log (pinned) |
| No channel configured | `deps.channel()` is null | Reminder `failed` | Log |
| Feed unreachable / non-2xx / too big / not ICS | Sync guard | Data kept; failure counter; alert at 3 | Sources (red), Log, one push |
| Unknown TZID / RDATE in feed | Parser | Best-effort + warning | Sources `last_result` |
| Cancelled single instance | Parser | Slot suppressed | — (correct behavior) |
| Ancient or dense recurrence | Expansion budget | `catching_up` (resumes) or `too_dense` (partial) | Event, Sources, Log |
| Bug throws inside one reminder / series / sync / maintenance | Per-step catch | Progress recorded, backoff applied | Log |
| Bug throws outside the steps | Top-level catch | Error floor 1 → 15 min backoff | Log → Background errors |
| Alarm replay | At-least-once semantics | Status check prevents re-send; only crash-between-send-and-write can duplicate | — |
| DO restart / deploy | Alarm persists in storage | Next alarm fires normally; migration on cold start | — |
| CPU limit exceeded on huge feed | Runtime error → counted as sync failure | Alert after 3; README guidance → Paid plan | Sources, Log |
| Domain changed | No key matches `RP_ID` | `setupRequired` → recovery flow | Login page, Settings (stale keys) |

## 15. Resource Budget (typical single-user load)

| Item | Estimate / day | Free limit |
|---|---|---|
| Alarm wakes: 3 sources × 48 syncs + 30 reminders + 1 maintenance + ~10 queue drains | ~185 | 100,000 requests (DO + Worker) |
| Web + API requests | < 1,000 | (same pool) |

## 18. Testing Strategy

- **Pure unit tests:** time zones (including New York and Berlin DST gaps and the fall-back overlap), ICS parsing (one fixture per row of §9), expansion, planning, and message formatting.
- **Differential test for the anchor:** for a set of rules (daily, weekly with `BYDAY` and `INTERVAL=2`, monthly `BYMONTHDAY=31`, yearly, with `COUNT`, with `UNTIL`, with `EXDATE`), expanding from an anchor must equal full expansion from `DTSTART` over the same window.
- **Durable Object integration tests** (`@cloudflare/vitest-pool-workers`): reconciliation, the queue, dispatch state machine, alarm arming and backoff, sync, auth flows, and HTTP routes. Clock, fetch, channel, and WebAuthn are injected.
- **Hot-loop tests:** for each alarm step, a permanently throwing fake proves that the next alarm is `≥ now + 60 s` after the first error, and that progress fields were written.
- **End-to-end smoke test:** Playwright with a Chrome DevTools Protocol virtual authenticator, running setup → register → create event → logout → passkey login.
- **On deploy:** measure the CPU time of one large-feed sync (§3).

## 19. Decisions

**Confirmed by the user (2026-11-17)**
- Bark only in v1; Telegram later, behind the channel interface.
- A custom domain or `workers.dev` are both fine, fixed once; if the domain ever changes, fall back to the recovery code and re-register keys.
- Passkeys with multiple keys and a recovery-code fallback; single Durable Object + alarm; no KV.

**Defaults chosen by Claude (revisable)**
- Manual events in the web UI; 60-day reminder window; 90-day history retention.
- Default lead 15 min; all-day reminders at 09:00 with no lead times; week starts Monday; English UI.
- Sync every 30 min (minimum 15), 5 MB cap, alert after 3 consecutive failures.
- One initial attempt + 3 retries (+1/+5/+15 min); late threshold 2 min; skip if the event already started.
- API tokens may read all events but write only `api`-origin events; `api` events can be deleted but not edited on the web.
- The recovery code also gates first-time setup and stays valid until rotated.
- Better an extremely rare duplicate than a missed reminder.
- No `occurrences` table; `reminders` is the schedule and `deliveries` is the history.
- Bulk reconciliation through a queue (10 series per wake); expansion anchor + 2,000-slot budget; per-step error isolation with exponential backoff (1 → 15 min).
- `userVerification: 'preferred'` without requiring it; confirmation required before revoking the last valid passkey.
- Cancelled instances become EXDATEs; `RDATE` is not supported in v1 (reported as a warning).
